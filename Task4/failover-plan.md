# План аварийного восстановления и переключения (Failover & Disaster Recovery Plan) — Africa Delivery MVP

Настоящий документ является операционной инструкцией для дежурного инженерного персонала при фиксации полной недоступности центральной инфраструктуры или локальных контуров платформы.

## 1. Сценарий 1: Катастрофический отказ центрального региона AWS (af-south-1, Кейптаун)

### 1.1. Критерий активации и лицо, принимающее решение
* **Триггер:** Полная недоступность API Gateway и эндпоинтов монолита (100% ошибок связи по метрикам Route53) в течение более 15 минут непрерывно. AWS Dashboard подтверждает глобальный сбой региона (Region Outage).
* **Ответственный за запуск плана:** Дежурный инженер из числа 6 инженеров-контракторов фиксирует инцидент по алерту Prometheus, объявляет статус Severity-1 и осуществляет экстренный созвон с Техническим директором (СТО Раджешем Меноном). Решение о ручном подтверждении переключения на резервный контур во Франкфурте принимает строго СТО.

### 1.2. Пошаговый алгоритм переключения (Failover Steps)
1. **Изоляция упавшего контура:** Дежурный инженер через консоль управления DNS (Cloudflare) переводит входящий трафик домена `://africadelivery.com` на удержание (выставляется Maintenance-заглушка HTTP 503).
2. **Автоматическое развертывание резервного шасси:** Инженер запускает готовый Terraform-скрипт, который в автоматическом режиме инициализирует поднятие зеркальной виртуальной машины монолита Go в резервном европейском регионе (AWS eu-central-1, Франкфурт). Время развертывания ОС и бинарного файла — 12 минут.
3. **Восстановление СУБД из реплицированного снапшота:** Вместо ручного разворачивания баз, инженер использует облачный механизм AWS RDS. Изменяется статус ежечасного автоматического снапшота, который AWS сам копировал из Кейптауна во Франкфурт в фоновом режиме (Promote Snapshot to Read/Write Master Instance). База данных инициализируется облаком автоматически за 15 минут.
4. **Актуализация сетевых маршрутов:** Перенастройка IPSec VPN-туннелей от сотовых операторов (MTN, Safaricom) на IP-адрес нового европейского шлюза API Gateway через запуск Ansible-скрипта.
5. **Запуск и проверка:** Проведение быстрого автоматического дымового тестирования (Smoke Test) транзакционного ядра. Переключение DNS-записи домена в Cloudflare с заглушки на боевой IP-адрес нового сервера во Франкфурте.

### 1.3. Целевые метрики восстановления и объемы потерь
* **Время восстановления (RTO):** Строго **до 4 часов** с момента утверждения решения СТО (фактическое время работы автоматических скриптов — около 45 минут, остальной лимит зарезервирован на ручную перенастройку стыков сотовыми операторами).
* **Допустимая потеря данных (RPO):** Максимум **1 час** транзакций. Данные, оформленные пользователями между моментом создания последнего автоматического снапшота AWS RDS и физическим падением дисков в Кейптауне, безвозвратно теряются. Данным пользователям после подъема системы автоматически высылается СМС с просьбой переоформить заказ.

## 2. Сценарий 2: Отказ локального ЦОД СУБД ПДн (Лагос / Найроби)

* **Триггер:** Потеря связи монолита Go с базой данных реальных ПДн конкретной страны (рост Connection Timeout > 5000мс).
* **Алгоритм автоматического переключения (Failover):**
  1. Внутренний модуль токенизации монолита фиксирует падение основного сервера базы данных (Primary).
  2. Включается встроенный механизм скрипта переключения: монолит автоматически перенаправляет все SQL-запросы на чтение и запись на резервный сервер-реплику (**Replica/Slave**), развернутый в соседней изолированной стойке того же национального ЦОД.
  3. Репликация между Primary и Replica осуществляется асинхронно в непрерывном режиме, благодаря чему показатели потерь данных (RPO) при локальном сбое стремятся к **0 секунд**.
  4. Время автоматического подхвата сессий репликой (RTO) составляет **не более 30 секунд**, процесс полностью прозрачен для конечных пользователей маркетплейса.
