# Architectural Decision Record (ADR) №002: Стратегия кэширования платформы Africa Delivery

## Статус
Предложено

## Контекст (Context)
В рамках запуска MVP-контура платформы Africa Delivery ожидаются краткосрочные пиковые нагрузки (до 10 000 одновременных активных сессий) в периоды проведения флеш-распродаж и live-трансляций. При этом действуют жесткие инфраструктурные ограничения: лимит бюджета CFO в \$5 000 в месяц на регулярные ИТ-расходы и использование единой СУБД PostgreSQL для модульного монолита. 

Без внедрения эффективной многоуровневой стратегии кэширования входящий поток запросов на чтение каталога неизбежно приведет к деградации производительности СУБД (CPU и дискового I/O), превышению допустимого Latency P99 (> 1.5 сек) и нарушению целевого SLA (99.9%). Использование отдельного выделенного enterprise-кластера кэширования (например, Redis) на этапе MVP отклонено в целях экономии бюджета.

## Решение (Decision)
Утвердить двухслойную архитектуру кэширования данных без развертывания дополнительных инфраструктурных компонентов:
1. **Внешний слой (Edge Caching):** Использование распределенной сети доставки контента (CDN) для кэширования статических медиа-ресурсов.
2. **Внутренний слой (In-Memory Caching):** Использование оперативной памяти самого монолитного приложения на Go (паттерн *Cache-Aside* на базе in-memory структур данных) для кэширования текстовых и слабоизменяемых компонентов каталога.

## Детализация параметров кэширования данных

| Сущность / Тип данных | Уровень размещения | Стратегия (Паттерн) | Время жизни (TTL) | Логика инвалидации кэша |
| :--- | :--- | :--- | :--- | :--- |
| **Медиа-контент (Фотографии товаров в формате WebP, баннеры, элементы интерфейса)** | Внешний (CDN Edge Servers в Нигерии и Кении) | Edge-кэширование статики | **30 дней** | Инвалидация по таймауту TTL. Принудительное обновление реализуется методом версионирования имен файлов (URL-versioning, например `img.webp?v=2`) со стороны WhatsApp-бота продавца. |
| **Статический каталог (Список категорий, текстовые описания и атрибуты SKU)** | Внутренний (In-Memory кэш приложения на Go) | Cache-Aside | **24 часа** | Автоматически по истечении TTL. Принудительная инвалидация происходит только при удалении товара продавцом или изменении текстовых характеристик администратором бэк-офиса. |
| **Анонсы флеш-распродаж (Списки SKU и таймеры на главном экране)** | Внутренний (In-Memory кэш приложения на Go) | Cache-Aside | **5 минут** | Автоматически по истечении TTL. Короткий интервал гарантирует актуальность расписания маркетинговых кампаний для пользователей без создания нагрузки на СУБД. |
| **Информационные остатки SKU (Отображение количества для витрины)** | Внутренний (In-Memory кэш приложения на Go) | Cache-Aside | **5 секунд** | Строго по истечении TTL. Короткое время жизни кэша обеспечивает баланс между визуальной актуальностью данных для покупателя и защитой СУБД от потока запросов на чтение. |

## Накладываемые ограничения и компромиссы (Consequences)
1. **Запрет на кэширование транзакционных остатков:** В целях предотвращения гонки условий (Race Conditions) и дефицита товара (Overbooking) в пиковые периоды флеш-распродаж, операции верификации и уменьшения складских остатков при оформлении заказов выполняются напрямую в СУБД PostgreSQL посредством атомарных SQL-запросов на запись, минуя любые слои кэширования.
2. **Эффект устаревания данных (Staleness):** Архитектурно принимается допущение, что покупатель на витрине может видеть остаток товара с задержкой до 5 секунд (в рамках TTL информационных остатков). Попытка покупки фактически закончившегося товара будет корректно перехвачена на этапе транзакционной проверки в СУБД с выдачей понятной ошибки пользователю.
3. **Экономия операционной памяти:** Поскольку in-memory кэш живет внутри единого процесса Go-монолита, для защиты сервера от утечек памяти (Out-of-Memory) кэшированию подлежат исключительно текстовые UUID-ключи и плоские структуры данных. Общий лимит RAM под внутренний кэш жестко ограничивается на уровне конфигурации приложения.
